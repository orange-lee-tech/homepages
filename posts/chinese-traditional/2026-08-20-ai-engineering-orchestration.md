<p class="post-lede">這不是一次「把三個工具連起來」的配置記錄，而是我在連續項目中逐漸形成的一套工程管理方法：先規定事實在哪裏、修改在哪裏發生、結果由什麼驗證，再讓 AI 進入流程。</p>

## 工具越多，不代表工程越順

個人網站項目早期最容易出現的問題並不是「AI 不會寫代碼」，而是工程狀態混亂：聊天裏說已經改了，GitHub 裏未必有；遠端倉庫已經更新，本地目錄可能還是舊版本；一次修改跨越太多文件，出錯以後很難判斷應該回到哪裏。

這些問題反覆出現後，我開始意識到，AI 協作真正缺少的不是更強的提示詞，而是**控制面**。

於是我逐漸把 ChatGPT、GitHub 與 PowerShell 的職責拆開。

| 角色 | 主要職責 |
| --- | --- |
| GitHub | 事實源、版本邊界、變更歷史與回滾點 |
| PowerShell | 本地工作台：檢查目錄、安裝依賴、構建、運行、測試與驗證 |
| AI | 方案設計、代碼修改、差異核對、問題定位、文檔與交接 |
| 人 | 判斷目標、接受風險、完成關鍵驗收並決定是否進入主線 |

這套分工最重要的一點是：**聊天內容不能代替倉庫狀態，AI 的判斷也不能代替工程驗證。**

## 從「生成代碼」轉向「管理變更」

當 AI 能夠一次生成大量代碼以後，真正昂貴的環節反而變成了判斷和驗證。

因此後來的工作流越來越固定：

1. 先讀取倉庫真實狀態，而不是依賴上一段對話的記憶；
2. 把目標切成能夠獨立檢查的小批次；
3. 修改後先看 diff，確認沒有誤傷；
4. 在 PowerShell 中執行構建、檢查或真實運行；
5. 只有驗證通過，才形成原子提交；
6. 每個階段保留明確的回滾點和交接文檔；
7. 新對話接手時，優先讀取倉庫、施工說明和當前狀態，而不是重新猜項目歷史。

這種方式看起來比「讓 AI 一口氣做完」更慢，但項目越長，它越快。

因為返工成本、上下文漂移和錯誤累積都會被提前截斷。

> **AI 給出答案，不等於工程上已經成立。**

只有代碼、構建、運行結果、倉庫狀態與人工驗收相互一致，任務才算真正完成。

## PowerShell 的意義不是「會敲命令」

PowerShell 在這套體系裏不是 GitHub 的替代品，也不是單純為了顯得技術化。

它更像項目的本地機房和值班室。

我用它確認：

- 當前到底在哪個目錄；
- 本地文件是否與倉庫一致；
- 依賴有沒有安裝完整；
- 構建是否真的通過；
- 軟件能不能啟動；
- 日誌暴露的是代碼問題、環境問題還是第三方服務問題；
- 一次失敗之後應該清理什麼、保留什麼；
- 修改後的版本是否具備繼續測試的條件。

這使「看起來正確」與「實際可以運行」之間多了一道現實檢查。

## GitHub 的意義也不只是保存代碼

GitHub 最重要的作用，是讓項目擁有**可追溯的事實歷史**。

一個好的提交應該回答：這一小批變化為什麼發生、改了什麼、驗證到什麼程度，以及如果它失敗應該退回哪裏。

於是提交不再只是「保存進度」，而成為工程管理的節拍器。

尤其在長週期 AI 協作中，GitHub 能抵抗一個很現實的問題：對話會越來越長，模型上下文會變化，但提交歷史、文件內容和版本邊界不會跟著聊天語氣漂移。

## 交接本身也是工程資產

當一個項目跨越多個對話、多個階段甚至不同 AI 時，「如何讓下一位接手者快速獲得正確上下文」開始成為真實成本。

因此我後來會專門維護：

- 當前事實源；
- 已完成事項；
- 已知風險；
- 不要重複踩的坑；
- 構建與驗證命令；
- 關鍵文件位置；
- 下一階段的邊界；
- 需要人工決定的事項。

這些材料最初只是為了少解釋幾遍，後來逐漸變成一種工程資產：它們降低了人員或 Agent 更換時的切換成本。

## 最終形成的不是工具鏈，而是一套管理順序

回頭看，這套體系真正穩定下來的不是某個軟件版本，而是一套順序：

> **事實源 → 任務切片 → 修改 → 驗證 → 提交 → 交接。**

它可以用在個人網站，也可以遷移到瀏覽器插件、桌面軟件、AI Agent 或其他長期維護項目。

工具當然會換。ChatGPT、GitHub、PowerShell 未來都可能被新的產品替代。

但工程管理的幾個問題不會消失：

- 誰擁有事實？
- 誰可以修改？
- 什麼證據證明修改成立？
- 什麼條件下允許進入主線？
- 出錯以後如何恢復？
- 下一位接手者如何知道現在到底發生了什麼？

對我來說，這才是 AI 編程真正帶來的能力升級：不是「讓 AI 替我寫更多代碼」，而是開始學習怎樣管理一個由人、模型、倉庫、運行環境和外部服務共同組成的生產系統。
