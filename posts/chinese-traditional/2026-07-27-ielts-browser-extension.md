2026 年 7 月下旬，在準備 9 月 23 日雅思機考的過程中，我完成了 IELTS Learning Assistant 的第一版。

它不是一個新的刷題平臺，而是一個獨立的瀏覽器側欄插件：在同桌英語、雅思哥或普通英文網頁上，把一次性的練習痕跡沉澱為自己的詞彙、原句、錯因、標籤和復盤資料。

最終產物也許只是一件精美的玩具，但它完成了從真實痛點、產品抽象、技術實現，到構建、分享、維護和商業化想像的閉環。

## 01｜它從一個很小的“不順手”開始

我先連續使用了幾天同桌英語機考平臺。它的題庫、播放器和機考還原度都不錯，但進入精聽頁面後，我很快遇到一個反覆出現的問題：漏聽的詞、沒反應過來的句子、連讀和弱讀原因，無法直接在學習現場記錄下來。

我又下載了雅思哥，希望找到更好的筆記與錯題復盤功能。結果發現，兩類平臺的核心邏輯都更接近“做題與看解析”，而不是“建立個人知識庫”。它們能告訴我哪一道題錯了，卻很難長期回答：

- 我為什麼錯？
- 這個表達在哪些題裡出現過？
- 以後應該怎樣複習？
- 能否保留原句和網頁來源，而不是隻記一個孤立單詞？

問題於是從“哪個雅思軟件有筆記功能”，變成了：

> 能不能在所有學習網頁之上，加一層屬於自己的知識管理？

這一步看似只是換了一個問法，實際上已經從“挑選工具”進入了“定義產品”。我不再試圖尋找一個完美平臺，而是把現有平臺繼續用於練習，把筆記、錯因、標籤和復盤交給一個獨立插件。

## 02｜我們最終做出了什麼

IELTS Learning Assistant 的定位非常剋制：**本地優先、瀏覽器側欄、專注捕獲與復盤**。

它不替代同桌英語，也不和雅思哥競爭；它只負責把用戶在網頁中的一次性學習行為，變成可編輯、可分類、可檢索、可導出的個人資料。

| 能力 | 具體表現 |
| --- | --- |
| 網頁捕獲 | 打開側欄，捕獲普通網頁中選中的英文文本 |
| 結構化記錄 | 保存詞彙、語境原句、自由筆記、錯因和自定義標籤 |
| 劍雅分類 | 可選擇劍雅 21 至劍雅 4，並按題庫年份整理 Library |
| 來源關聯 | 持續關聯原句和原網頁鏈接，避免脫離語境 |
| 編輯與管理 | 支持再次編輯、保存、複製或刪除單條記錄 |
| 導出與備份 | 支持複製全部記錄，或導出 UTF-8 Markdown |
| 多瀏覽器構建 | 同一套源碼構建 Chrome、Edge 和 Firefox |
| 數據兼容 | 繼續讀取舊版 `ieltsNotes`，舊記錄可補充字段後重新歸類 |

插件運行時不連接 AI 服務、遠程服務器或 GitHub，也不依賴 VPN。所有學習記錄保存在瀏覽器擴展本地存儲中。

這個選擇並不“高級”，卻讓第一版的邊界非常清楚：零服務器成本、隱私路徑簡單、安裝後即可長期使用。

> 小項目最容易犯的錯誤，不是功能太少，而是第一版就急著加入賬號、雲同步、AI、會員與後臺，最後什麼都做不穩。

第一版先把“捕獲—整理—復盤—備份”做完整。

## 03｜它像一件精美的玩具，但不是空殼

我願意把這個插件稱作“一件精美的玩具”。

它沒有複雜賬號系統，沒有云端數據庫，沒有真正的 AI Tutor，也沒有龐大的用戶量。它解決的只是一個非常具體的問題：精聽和閱讀時，把值得留下的內容順手記下來。

但“玩具”不等於隨手拼出的演示。這個項目已經具備一件可交付軟件應有的基本閉環：

- **能安裝**：開發模式加載後可以在真實瀏覽器中使用，而不是停留在代碼預覽；
- **能保存**：數據寫入瀏覽器本地存儲，關閉頁面後仍然保留；
- **能升級**：舊筆記不會因為字段變化被直接丟棄，而是進入“未分類舊筆記”；
- **能分享**：構建產物可壓縮發送，接收者解壓後加載即可使用；
- **能維護**：倉庫記錄了拉取、構建、提交、推送和高風險命令邊界；
- **能擴展**：未來可以繼續加入搜索、複習算法、AI 分析與跨設備同步。

所謂“產品感”，並不一定來自功能數量。很多時候，它來自邊界清楚、交互順手、數據不會丟、升級不會亂、別人能夠安裝、未來還能繼續修改。

表面很輕，內部卻已經開始形成工程秩序。

## 04｜從九辰官網的 60 小時，到雅思插件的 2 小時

這不是工作量從 60 小時縮水為 2 小時，而是能力開始複用。

九辰教育官網 V1.0 是前一個里程碑。它大約佔用了 60 個“人類小時”，包含業務資料整理、31 個靜態頁面、案例與師資內容治理、獨立域名、HTTPS、ICP備案、公安備案、雲服務器、Nginx、搜索引擎基礎配置和正式上線驗收。那是一次完整的企業級門戶交付。

IELTS 插件只佔用了約 2 個“人類小時”。兩者不能按代碼量或複雜度直接比較。真正值得比較的是：在官網項目裡被迫學會的需求拆解、範圍控制、Git 管理、構建驗證、錯誤排查和交接意識，已經變成了可以被快速調用的能力。

| 維度 | 九辰教育官網 | IELTS Learning Assistant |
| --- | --- | --- |
| 問題來源 | 企業品牌、內容、諮詢與合規需求 | 個人備考中的精聽筆記與復盤痛點 |
| 人類投入 | 約 60 小時 | 約 2 小時 |
| 工程規模 | 31 個靜態頁面、雲服務器與備案閉環 | 瀏覽器側欄、本地存儲與三端構建 |
| 主要難點 | 信息架構、公開邊界、部署與線上故障 | 產品邊界、數據結構、瀏覽器兼容 |
| 共同方法 | 需求拆解、GitHub、構建、驗收、交接 | 需求拆解、GitHub、構建、驗收、交接 |
| 能力意義 | 第一次組織 AI 完成真實企業交付 | 第一次把能力遷移為個人產品 |

> 60 小時不是被 2 小時“替代”了。那 60 小時沉澱出的判斷力、工程語言和協作方法，恰恰是後面 2 小時能夠成立的原因。

## 05｜我與 AI 的協作方式，已經從“聊天”變成“推進項目”

為了避免工程性對話在長上下文中失控，我先結束了前面的討論，把背景、痛點、功能藍圖、技術路線和開發階段整理成一份交接信息，再開啟新的構建對話。

這個動作看起來很“行政”，卻讓 AI 從第一輪開始就知道：

- 項目要解決什麼；
- 第一版不做什麼；
- 哪些數據必須保留；
- 怎樣才算完成。

實際推進不是一句“幫我做個插件”，而是一條可驗證的鏈路：

> 明確目標 → 讀取現狀 → 選擇模板 → 限定修改範圍 → 運行構建 → 瀏覽器加載 → 反饋問題 → 修正 → Git 提交 → 編寫交接

技術上，項目借用了 WXT、React 和 TypeScript 的現成模板。所謂“從零開始”，並不是拒絕模板、庫和框架，也不是每一行代碼都必須從空白文本敲出；它指的是此前沒有完整做過這類作品，而這一次第一次獨立走完需求、結構、取捨、驗收和交付。

> 借模板不是減分。真正的問題，是隻會複製外殼，卻不知道為什麼這樣設計、哪裡應該刪、哪裡必須改、怎樣驗證它仍然可靠。

## 06｜即使只有兩小時，工程管理仍然是精髓

小項目很容易讓人放鬆警惕：功能不多、代碼不長、似乎改壞了也可以重來。但恰恰是在這種項目裡，是否擁有工程管理意識最容易看出差別。

1. **範圍邊界**：第一版只解決捕獲、記錄、分類、復盤與導出，不急著做 AI Tutor。
2. **數據邊界**：學習記錄默認保存在瀏覽器本地，並提供 Markdown 備份出口。
3. **兼容邊界**：繼續讀取舊版 `ieltsNotes`，避免升級直接破壞已有記錄。
4. **平臺邊界**：用同一套源碼構建 Chrome、Edge 和 Firefox，減少分叉維護。
5. **變更邊界**：以 main、commit 和 diff 為事實，不使用不明原因的 force、hard reset。
6. **驗收邊界**：通過 TypeScript 檢查、三端構建、瀏覽器加載和真實操作確認完成。

倉庫中的維護說明甚至明確列出了不應在原因不明時使用的高風險命令：`git push --force`、`git reset --hard`、`git clean -fd`、`npm audit fix --force`。

它們不是複雜技術，卻代表一種重要習慣：不為了“快點恢復正常”而破壞可追蹤性。

> 不會工程管理的人，會被 AI 的速度反噬；懂得結構、依賴與驗收的人，才能把速度變成真正的進度。

## 07｜從第一個網站，到第一個插件，我真正提升了什麼

九辰官網和雅思插件，一個是企業門戶，一個是個人學習工具；一個需要服務器、備案和大量內容治理，一個只需要瀏覽器、本地數據和幾張界面。

它們在外觀上幾乎沒有關係，但在能力路徑上卻是連續的：

- **從表達需求，到定義問題**：不只告訴 AI “做什麼”，還要明確為什麼做、誰使用、什麼不做；
- **從生成代碼，到組織交付**：關注倉庫、分支、構建、產物、安裝與交接，而不只關注聊天回覆；
- **從解決任務，到抽象產品**：把個人精聽痛點抽象成可跨網站使用的瀏覽器學習層；
- **從一次項目，到能力複用**：把官網項目形成的管理方法遷移到更短、更輕的插件開發；
- **從拿來主義，到吸收再設計**：使用模板與框架，但按真實問題重構字段、流程和產品邊界；
- **從完成作品，到看見資產**：開始意識到插件、網站和 App 也可以成為可傳播、可維護的互聯網資產。

真正的“從零”，是過去沒有走過這條路，而現在第一次把完整的方法鏈條建立起來，並知道下一次可以怎樣更快、更穩地再走一遍。

## 08｜我也順便瞥了一眼商業化潛力

插件完成之後，我自然開始考慮：它是否可以上架 Edge 擴展市場，免費對外開放？免費版和付費版對開發者意味著什麼？一個規模很小的工具，怎樣從個人需求逐漸形成可持續的互聯網資產？

當前版本仍然保持本地優先，沒有服務器與 AI 成本，適合作為免費核心工具。未來真正有可能形成付費價值的，並不是把“記筆記”鎖起來，而是在用戶願意付費的複雜層上增加服務：

| 層級 | 可能提供的價值 | 現階段態度 |
| --- | --- | --- |
| 免費核心 | 捕獲、筆記、標籤、Library、Markdown 導出 | 保持簡單、隱私清楚、便於傳播 |
| 專業增強 | AI 語音現象分析、同義替換、智能複習與跨設備同步 | 未來探索，不能破壞本地體驗 |
| 服務化能力 | 教師工作臺、班級資料、團隊協作或垂直課程配套 | 需要真實用戶與長期驗證 |

> 商業化潛力不是給玩具貼上價格標籤，而是看它是否持續解決問題、是否擁有清晰邊界、是否能夠分發、維護和積累用戶反饋。

這還不是一份商業計劃，只是一次視野變化：以前我把網站和插件看成“完成後就結束的技術作品”；現在開始意識到，它們也可能成為可以持續迭代、公開分發、形成聲譽乃至產生收入的數字資產。

## 09｜結語：插件很小，但能力遷移是真實的

回頭看，這個項目並不宏大。它沒有解決雅思學習的全部問題，也沒有證明我已經成為專業插件開發者。

它只是讓我在真實使用中發現一個摩擦，把摩擦抽象為產品，再借助 AI、模板、GitHub 和已經形成的工程習慣，把它變成了可以安裝和使用的第一件瀏覽器作品。

九辰官網讓我第一次理解：網站上線只是表面，真正上線的是一種組織 AI 完成複雜項目的能力。IELTS Learning Assistant 則進一步證明，這種能力並沒有被鎖在原項目裡，它可以遷移到新的領域，壓縮新的試錯成本，並開始產生產品意識。

> 不是 AI 用兩小時替我做了一個插件，而是我用前一個項目訓練出的判斷力和工程管理能力，在兩小時裡組織 AI 完成了一個更輕、更快、更接近產品的閉環。

未來還會有第二個插件、第二個網站，也可能會有真正對外運營的 App。重要的不是每一件作品都足夠大，而是這些作品開始連接起來：學習提高判斷力，判斷力提高工具效率，工具效率釋放新的實踐空間，新的實踐又反過來提升能力。
