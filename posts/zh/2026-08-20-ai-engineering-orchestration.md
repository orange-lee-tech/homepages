<p class="post-lede">这不是一次“把三个工具连起来”的配置记录，而是我在连续项目中逐渐形成的一套工程管理方法：先规定事实在哪里、修改在哪里发生、结果由什么验证，再让 AI 进入流程。</p>

## 工具越多，不代表工程越顺

个人网站项目早期最容易出现的问题并不是“AI 不会写代码”，而是工程状态混乱：聊天里说已经改了，GitHub 里未必有；远端仓库已经更新，本地目录可能还是旧版本；一次修改跨越太多文件，出错以后很难判断应该回到哪里。

这些问题反复出现后，我开始意识到，AI 协作真正缺少的不是更强的提示词，而是**控制面**。

于是我逐渐把 ChatGPT、GitHub 与 PowerShell 的职责拆开。

| 角色 | 主要职责 |
| --- | --- |
| GitHub | 事实源、版本边界、变更历史与回滚点 |
| PowerShell | 本地工作台：检查目录、安装依赖、构建、运行、测试与验证 |
| AI | 方案设计、代码修改、差异核对、问题定位、文档与交接 |
| 人 | 判断目标、接受风险、完成关键验收并决定是否进入主线 |

这套分工最重要的一点是：**聊天内容不能代替仓库状态，AI 的判断也不能代替工程验证。**

## 从“生成代码”转向“管理变更”

当 AI 能够一次生成大量代码以后，真正昂贵的环节反而变成了判断和验证。

因此后来的工作流越来越固定：

1. 先读取仓库真实状态，而不是依赖上一段对话的记忆；
2. 把目标切成能够独立检查的小批次；
3. 修改后先看 diff，确认没有误伤；
4. 在 PowerShell 中执行构建、检查或真实运行；
5. 只有验证通过，才形成原子提交；
6. 每个阶段保留明确的回滚点和交接文档；
7. 新对话接手时，优先读取仓库、施工说明和当前状态，而不是重新猜项目历史。

这种方式看起来比“让 AI 一口气做完”更慢，但项目越长，它越快。

因为返工成本、上下文漂移和错误累积都会被提前截断。

> **AI 给出答案，不等于工程上已经成立。**

只有代码、构建、运行结果、仓库状态与人工验收相互一致，任务才算真正完成。

## PowerShell 的意义不是“会敲命令”

PowerShell 在这套体系里不是 GitHub 的替代品，也不是单纯为了显得技术化。

它更像项目的本地机房和值班室。

我用它确认：

- 当前到底在哪个目录；
- 本地文件是否与仓库一致；
- 依赖有没有安装完整；
- 构建是否真的通过；
- 软件能不能启动；
- 日志暴露的是代码问题、环境问题还是第三方服务问题；
- 一次失败之后应该清理什么、保留什么；
- 修改后的版本是否具备继续测试的条件。

这使“看起来正确”与“实际可以运行”之间多了一道现实检查。

## GitHub 的意义也不只是保存代码

GitHub 最重要的作用，是让项目拥有**可追溯的事实历史**。

一个好的提交应该回答：这一小批变化为什么发生、改了什么、验证到什么程度，以及如果它失败应该退回哪里。

于是提交不再只是“保存进度”，而成为工程管理的节拍器。

尤其在长周期 AI 协作中，GitHub 能抵抗一个很现实的问题：对话会越来越长，模型上下文会变化，但提交历史、文件内容和版本边界不会跟着聊天语气漂移。

## 交接本身也是工程资产

当一个项目跨越多个对话、多个阶段甚至不同 AI 时，“如何让下一位接手者快速获得正确上下文”开始成为真实成本。

因此我后来会专门维护：

- 当前事实源；
- 已完成事项；
- 已知风险；
- 不要重复踩的坑；
- 构建与验证命令；
- 关键文件位置；
- 下一阶段的边界；
- 需要人工决定的事项。

这些材料最初只是为了少解释几遍，后来逐渐变成一种工程资产：它们降低了人员或 Agent 更换时的切换成本。

## 最终形成的不是工具链，而是一套管理顺序

回头看，这套体系真正稳定下来的不是某个软件版本，而是一套顺序：

> **事实源 → 任务切片 → 修改 → 验证 → 提交 → 交接。**

它可以用在个人网站，也可以迁移到浏览器插件、桌面软件、AI Agent 或其他长期维护项目。

工具当然会换。ChatGPT、GitHub、PowerShell 未来都可能被新的产品替代。

但工程管理的几个问题不会消失：

- 谁拥有事实？
- 谁可以修改？
- 什么证据证明修改成立？
- 什么条件下允许进入主线？
- 出错以后如何恢复？
- 下一位接手者如何知道现在到底发生了什么？

对我来说，这才是 AI 编程真正带来的能力升级：不是“让 AI 替我写更多代码”，而是开始学习怎样管理一个由人、模型、仓库、运行环境和外部服务共同组成的生产系统。
